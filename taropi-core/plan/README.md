# Plan Workflow / 三阶段状态机

`/plan 任务描述` 将调研、确认和实施串成闭环。

1. **计划制定**：保持当前模型和工具声明，随任务一次性发送规划规则。通过 `tool_call` 拦截 `edit`、`write`，禁止通过其他工具绕过只读限制。掌握背景后，若仍有不确定部分，主 Agent 会通过提问与用户反复确认；达到 99% 一致性后才输出带有 `Plan:` 的详细计划。
2. **澄清确认**：TUI 将计划写入固定目录 `.pi/taropi/plans/`，并直接展示完整文件地址。用户可选择开始实施，或输入补充内容后回到计划制定阶段；Esc 取消工作流，不自动发起新请求。RPC 使用标准选择和输入对话框，非交互模式不启动流程。
3. **实施**：确认后一次性发送实施任务，解除写工具拦截。模型、工具声明和历史始终不变，不自动压缩上下文。实施轮次结束后计划文件标记为已完成；模型请求失败或取消时不标记完成。

计划请求在模型报错或被取消后，会等待 Pi 完成自动重试；最终仍失败时清理工作流状态，允许重新执行 `/plan`。

## 请求前缀约束

不注册 `context`、`context_with_system`、`before_provider_request` 等请求改写钩子，不通过 `before_agent_start` 反复追加规则，不自动调用 `setModel`、`setActiveTools` 或 `compact`。这样避免计划阶段变更历史前缀，导致缓存失效和已签名 thinking 块的对话绑定不匹配。

历史会话中已有的 planning 提示不删除；本模块不会修复外部提供商配置、其他扩展改写或已损坏会话造成的 thinking 绑定错误。

## 模块结构

```text
plan/
├── index.ts    # 状态机、失败恢复、命令和事件处理
├── types.ts    # 工作流类型与空闲状态
├── store.ts    # 独立状态文件、版本校验与原子写入
├── file.ts     # 计划文件命名、写入和状态更新
├── prompts.ts  # 一次性计划制定规则
├── tui.ts      # 计划确认界面
├── sdk.test.ts # 真实 AgentSession 与模拟提供商的前缀回归
└── README.md   # 模块说明
```

## 计划文件

TUI 固定将计划文件写入当前工作目录下的：

```text
.pi/taropi/plans/计划标题-时间戳.md
```

确认界面会显示本次生成文件的绝对地址。文件名使用计划标题和时间戳，文件内容记录计划文本、创建时间、更新时间和当前状态。

## 会话恢复

工作流状态使用独立文件 `.pi/taropi/plan/<sessionId>.json`，带 schema 版本号、原子写入，不使用会话条目或消息存储状态。缺失、损坏或版本不匹配时降级为空闲；正常结束、取消和关闭会话时清理状态文件。

恢复会话后清理中断的工作流并保持空闲，历史计划文件保留；不恢复中断的规划或实施轮次，不读取旧 `plan-workflow` 会话条目。

## 验证边界

SDK 回归使用真实 `AgentSession` 和模拟提供商，验证带签名 thinking 的连续请求只在末尾追加、系统消息只有一条、模型及工具声明不变。该测试不访问网络，不能证明真实 API 的签名校验或缓存命中正常；发布前仍需单独验证真实请求和逐轮 `cacheRead`。
